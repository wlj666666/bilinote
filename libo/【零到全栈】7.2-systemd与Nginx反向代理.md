## 回顾与问题 [原片 @ 00:00](https://www.bilibili.com/video/BV18Yp96fETe?t=0)
上一节将 `zero-to-tech` 项目用朴素的方式发布到服务器，前后端都跑起来，但留下了几个尾巴：
1. **管理麻烦**：后端服务挂了不能自动重启，查看和停止进程的方式不优雅。
2. **安全脆弱**：`uvicorn` 直接监听 8000 端口对外暴露，没有安全控制，就像在“裸奔”；后续上 HTTPS 会很费劲。
3. **前后端认路不便**：前端配置文件里写死了服务器的 IP 地址和端口，后面如果换成域名会不方便。

下面展开说明这几个问题，并引入 `systemd`（进程守护）和反向代理来解决。

## 进程守护：systemd [原片 @ 07:27](https://www.bilibili.com/video/BV18Yp96fETe?t=447)

### 当前管理的痛点
- 用 `ps aux | grep FastAPI` 查看进程，会混入 grep 自身的进程，不优雅；若服务器上有多个 FastAPI 程序，更难分辨。
- 停止程序只能用 `kill <pid>`，查到进程号再杀，感觉 “low low 的”。
- `nohup` 写入日志文件 `backend.log`，文件名、路径全靠记忆，日志可能无限增大，曾出现日志塞满磁盘导致事故。
- `nohup` 方式运行的后端，**服务器重启后不会自动起来**；程序自己崩溃了也不会自行重启。
- 理想情况：程序崩溃或服务器重启后，程序应能自动重新运行，日志由管家统一管理。

### systemd 的作用
- “进程守护” 就是让一个专门的程序（管家）帮我们盯着、守护我们的后端程序。
- Ubuntu 上干这件事的是 `systemd`，`d` 代表 `daemon`（守护进程）。
- 之前操作 Nginx 时，早已在和 `systemd` 打交道：
  - `sudo systemctl status nginx` 查看 Nginx 状态（绿色的 `active (running)`）。
  - `sudo systemctl reload nginx` 重载配置。
  - 这些命令其实都是通过 `systemctl` 指挥 `systemd`，`systemctl` 是 `systemd` 的命令行工具（`control` 缩写）。
- Nginx 有自己的启动命令（如 `sudo nginx`、`nginx -s reload`），但后来把它委托给 `systemd` 做进程守护，日常就统一用 `systemctl` 管理。
- 这一节我们也将 `uvicorn` / FastAPI 后端委托给 `systemd`。

## 编写 service 文件 [原片 @ 13:00](https://www.bilibili.com/video/BV18Yp96fETe?t=780)

### service 文件结构
要把程序委托给 `systemd`，需要写一个 `.service` 文件，描述程序如何运行、如何管理。Nginx 就有自己的 service 文件，可通过 `systemctl cat nginx` 查看。  
service 文件通常包含三部分（参考 slide）：
- `[Unit]`：描述这个服务是什么、叫什么。
- `[Service]`：重点，定义怎么运行程序——命令、用户身份、崩溃后怎么办等。
- `[Install]`：指定何时启动，比如开机自启相关配置。

具体语法不需要背，可以让 AI 帮忙写，关键是**知道有这个文件、了解大致结构**。

### 为后端创建 zero-backend.service
1. **文件位置**：`/etc/systemd/system/zero-backend.service`（固定目录，文件名自己起，不要和已有服务重名）。
2. **创建文件**：用 `sudo touch` 创建空文件，再用 `sudo vim` 编辑。
3. **填充内容**（可从课件网站复制，实际项目可让 AI 生成）：
   - `Description`：给人看的描述。
   - `User`：用谁的身份运行，这里填 `ubuntu`（用自己登录的账号，权限够用就好，不建议用 root）。
   - `WorkingDirectory`：程序的工作目录，指向项目后端所在的实际路径。
   - `ExecStart`：启动命令。直接写 FastAPI 的完整路径（`/home/ubuntu/zero-to-tech/backend/venv/bin/fastapi run`），这样就不需要先激活虚拟环境。
   - `Restart=always`：进程一死立刻重新拉起来。
   - `WantedBy=multi-user.target`：固定写法，实现开机自启。

4. **让 systemd 生效**：
   - `sudo systemctl daemon-reload` —— 通知 systemd 重新读取 service 文件。
   - `sudo systemctl start zero-backend` —— 启动服务。
   - `sudo systemctl status zero-backend` —— 看到 `active (running)` 和 PID，说明已由 systemd 接管。
   - `sudo systemctl enable zero-backend` —— 设置为开机自启。

5. **验证进程守护**：用 `kill <pid>` 模拟进程意外死亡，再用 `status` 查看，会发现 PID 已变，进程被自动重新拉起来了——这正是 `Restart=always` 的效果。

## 管理服务与查看日志 [原片 @ 25:46](https://www.bilibili.com/video/BV18Yp96fETe?t=1546)

### 常用 systemctl 命令
- `systemctl start/stop/restart/reload/enable/disable/status <service>`  
- 注意：**`systemctl stop`** 是正式通知 systemd 停止服务，停止后不会自动重启；而 `kill` 是绕过 systemd 直接杀进程，systemd 视作意外，会立即重新拉起。

### 日志管理
- 之前用 `nohup` 写 `backend.log`，现在日志一起交给 systemd 管理，有容量上限，会自动清理旧日志。
- `journalctl` 是查看 systemd 日志的工具：
  - `-u zero-backend` 指定服务。
  - `-n 50` 只看最后 50 行。
  - `-f` 实时跟随（最常用），方便一边操作一边观察后端输出。
- 按 `Ctrl+C` 退出跟随。原有 `backend.log` 不再更新，可直接删除，避免误导。

## 反向代理：让 Nginx 站在前面 [原片 @ 33:20](https://www.bilibili.com/video/BV18Yp96fETe?t=2000)

### Nginx 与 uvicorn 的分工
目前前端静态文件由 Nginx 提供（监听 80），后端 uvicorn 监听 8000，两者都直接对外服务。但它们擅长的东西不同：
- **Nginx** 擅长对外服务：访客日志（access log）、HTTPS 一行命令搞定、压缩缓存等提速功能开箱即用。
- **uvicorn** 本职是跑 Python 代码，对外服务只是“兼职”，没有独立的访客日志，上 HTTPS 麻烦，缺少性能优化功能。
- 业内普遍做法：**让 Nginx 站在前面**，全职对外，处理互联网上的各种请求；uvicorn 只对内，专心跑 Python，不再直接与用户打交道。

### 请求分发规则
- Nginx 只监听 **80** 端口。
- 按照路径判断：
  - 所有以 `/api/` 开头的请求，转发给内部 8000 端口的 uvicorn 处理。
  - 其他请求，作为前端静态文件直接由 Nginx 返回（主页、`/text-lab` 等）。
- 此前可访问的后端文档地址（如 `/docs`）不是 `/api/` 开头，改造后将无法通过 80 访问，但这本就是合理的：文档是给开发者用的，本不该暴露给最终用户。

## 配置 Nginx 反向代理 [原片 @ 42:24](https://www.bilibili.com/video/BV18Yp96fETe?t=2544)

编辑 `/etc/nginx/sites-enabled/default`，在原有的 `server` 块内新增一个 `location`：

```
location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

- `proxy_pass http://127.0.0.1:8000;` —— 注意**末尾不要加斜杠**。若写成 `http://127.0.0.1:8000/`，Nginx 会吃掉 `/api/` 前缀，导致后端收到的路径错误，接口全部报 404。
- 下面四行 `proxy_set_header` 至关重要：用户的请求经过 Nginx 转发后，原始信息（真实 IP、域名、协议等）会丢失，这些头把用户信息传递给后端，务必保留，不可省略。
- 修改后先执行 `sudo nginx -t` 检查语法，再 `sudo systemctl reload nginx` 重载配置。

测试：直接在浏览器访问 `http://<服务器IP>/api/profile`（不用加 8000 端口），能正常拿回后端数据，说明反向代理已生效。

## 安全加固：两道防线 [原片 @ 48:42](https://www.bilibili.com/video/BV18Yp96fETe?t=2922)

现在所有流量都通过 80 端口进入，8000 端口没必要继续对外。加固分两步（“砍两刀”）：

1. **让 uvicorn 只监听本机**  
   编辑 `zero-backend.service`，在 `ExecStart` 的 `fastapi run` 后加上 `--host 127.0.0.1`，然后执行：
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl restart zero-backend
   ```
   再次查看状态，会显示监听在 `127.0.0.1:8000`。从外网直接访问 `<服务器IP>:8000` 将无法连接，但本机用 `curl` 请求 `127.0.0.1:8000/api/...` 依然可以拿到结果。

2. **在云防火墙删除 8000 端口规则**  
   进入云平台防火墙（如腾讯云），删除 8000 端口的放行规则，只保留必要的 80（HTTP）和 22（SSH）等。  
   这是“纵深防御”——万一程序配置不小心又暴露到 0.0.0.0，防火墙还能再拦一道。

## 前端配置：利用同源写相对路径 [原片 @ 54:31](https://www.bilibili.com/video/BV18Yp96fETe?t=3271)

经过反向代理，前后端已经同源（相同协议、IP/域名、端口）。  
修改前端生产环境配置 `.env.production`，将后端地址留空（`VITE_API_BASE_URL=`），而不是写死 IP 和端口。

- 前端代码会读取这个值作为 base，若为空则拼接路径时直接变成相对路径（如 `/api/history`）。
- 浏览器遇到相对路径会自动补上当前页面的地址，正好和后端同源，请求正确。
- 好处：以后换成域名或切换到 HTTPS，配置文件无需再改，前端构建一次即可。

修改配置后，在项目根目录执行 `npm run build` 重新构建前端。

## 验证与新状态 [原片 @ 57:39](https://www.bilibili.com/video/BV18Yp96fETe?t=3459)

从用户角度看网站功能不变，但底层方式已全部切换：
1. **Network 面板**：对后端的请求不再带 8000 端口，与前端同协议、同 IP、同端口，不再出现多余的 `OPTIONS` 预请求（因为已同源）。  
2. **外网无法直连 8000 端口**（之前已测通）。  
3. **进程自动重启**：`kill` 掉后端进程后，systemd 立刻将它拉起，服务自动恢复；甚至重启服务器后站点也都在。

满足这三点，部署算是真正“稳下来了”。  
注意：本地开发时 3000 访问 8000 仍然跨源，后端的 CORS 配置不要删。

## AI 总结
本节在上一节朴素部署的基础上，解决了三个遗留问题：管理脆弱、安全裸露、前后端硬编码地址。通过引入 `systemd` 进程守护，让 FastAPI 后端能开机自启、崩溃自动重启，且日志统一由 `journalctl` 管理。同时利用 Nginx 实现反向代理，所有流量统一到 80 端口，以 `/api/` 路径区分前后端请求；并设置两道防线——让 uvicorn 只监听本地地址，云防火墙关闭 8000 端口，增强安全性。前后端同源后，前端配置文件改为相对路径，减少未来更换域名或协议的改造成本。整体部署从“朴素可用”进入了更健壮、更安全的状态。
