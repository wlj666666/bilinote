可以把整个过程分成三部分：

1. 后端进程启动并等待任务
2. 前端开发服务器启动并提供网页文件
3. 浏览器下载网页代码、执行代码、画出界面

整体数据流是：

```text
┌──────────────┐
│ 浏览器        │
│ React 页面    │
└──────┬───────┘
       │ 访问 localhost:3016
       ▼
┌──────────────┐
│ 前端开发服务器 │  Node.js / Vite
│ 端口 3016     │
└──────┬───────┘
       │ /api 请求转发
       ▼
┌──────────────┐
│ 后端服务器     │  Python / FastAPI / Uvicorn
│ 端口 8483     │
└──────┬───────┘
       │
       ├── 下载字幕、音频或视频
       ├── 调用 GPU、OCR、语音识别
       ├── 调用 AI 模型
       └── 保存和返回笔记
```

## 一、启动后端时发生了什么

你运行：

```bash
conda activate bilinote
cd /home/unbekannter/bilinote/BiliNote/backend
bash start-gpu.sh
```

### 第一步：激活 Python 环境

```bash
conda activate bilinote
```

这一步不会启动后端，它只是修改当前终端的环境。

修改后，当你运行：

```bash
python
```

操作系统会使用 `bilinote` 环境里的 Python，以及这个环境安装的：

- FastAPI
- Uvicorn
- PyTorch
- OCR
- Whisper
- 其他 Python 依赖

可以理解成：

```text
激活前：
python → 系统默认 Python

激活后：
python → bilinote 专用 Python
```

### 第二步：进入后端目录

```bash
cd /home/unbekannter/bilinote/BiliNote/backend
```

这只是切换终端当前所在的目录。

后端代码里的相对路径，例如：

```text
note_results/
static/
uploads/
config/
```

都会以这个目录作为基础。

### 第三步：执行启动脚本

```bash
bash start-gpu.sh
```

`bash` 读取并逐行执行 `start-gpu.sh`。

这个脚本主要做这些事情：

```text
start-gpu.sh
│
├── 找到 Conda 环境里的 CUDA 库
├── 设置 GPU 动态库路径
├── 设置 OCR 使用 cuda
├── 设置 Whisper 计算类型
├── 设置任务并发数量
└── 执行 python main.py
```

脚本最后实际执行的是：

```bash
python main.py
```

其中使用了 `exec`，所以原来的 Shell 脚本进程会被 Python 进程替换。

### 第四步：Python 启动 FastAPI

`main.py` 会启动：

```text
FastAPI  → 定义后端有哪些接口
Uvicorn  → 真正负责接收 HTTP 网络请求
```

它会创建一个 Socket，并绑定：

```text
0.0.0.0:8483
```

这里需要修正我们前面简化后的说法：当前项目后端实际默认绑定的是 `0.0.0.0:8483`，因此它在所有 IPv4 网络接口的 `8483` 上监听。本机依然可以通过下面的地址访问：

```text
http://127.0.0.1:8483
```

然后后端还会做一些初始化：

- 初始化 SQLite 数据库
- 读取语音转写配置
- 初始化默认 AI 供应商
- 加载代理配置
- 恢复异常中断的任务
- 注册 API 接口

完成后，Python 进程不会退出，而是一直阻塞等待：

```text
有没有新的 HTTP 请求到达 8483？
```

此时后端已经准备好了，但你还看不到网页，因为后端主要提供数据和计算能力，不负责当前这个 React 页面。

## 二、启动前端时发生了什么

你在另一个终端运行：

```bash
cd /home/unbekannter/bilinote/BiliNote/BillNote_frontend
npm run dev
```

### 第一步：npm 读取 `package.json`

`npm run dev` 会在 `package.json` 里查找：

```json
{
  "scripts": {
    "dev": "vite"
  }
}
```

所以这条命令实际上是在运行：

```bash
vite
```

Vite 是前端开发服务器。

### 第二步：Vite 读取项目配置

Vite 读取 `vite.config.ts`，项目配置的默认端口是：

```text
3015
```

默认监听地址是：

```text
0.0.0.0
```

也就是：

```text
0.0.0.0:3015
```

但你的 Cursor 当时最终使用了 `3016`，很可能是因为 `3015` 已经被另一个进程占用。

由于项目没有设置：

```ts
strictPort: true
```

Vite 遇到端口占用时会尝试下一个端口：

```text
尝试 3015
   ↓ 被占用
尝试 3016
   ↓ 成功
```

于是 Vite 开始监听：

```text
0.0.0.0:3016
```

终端一般会显示类似：

```text
Local: http://localhost:3016/
```

### 第三步：Vite 等待浏览器请求

这时系统里至少有两个服务进程：

```text
Python/Uvicorn  → 监听 8483
Node/Vite       → 监听 3016
```

但网页还没有自动出现在浏览器中。Vite 只是准备好了网页代码，等待浏览器来请求。

## 三、浏览器访问 `localhost:3016` 时发生了什么

当你在地址栏输入：

```text
http://localhost:3016/
```

浏览器首先拆解这个 URL：

```text
http://localhost:3016/
│      │         │    │
│      │         │    └── 路径 /
│      │         └─────── 端口 3016
│      └───────────────── 主机名 localhost
└──────────────────────── 协议 HTTP
```

### 第一步：解析 `localhost`

操作系统把：

```text
localhost
```

解析成本机回环地址，通常是：

```text
127.0.0.1
```

因此浏览器实际上准备连接：

```text
127.0.0.1:3016
```

因为你使用 WSL，底层还可能经过 Windows 到 WSL 的 localhost 转发，不过从使用角度可以先理解为“访问本机 3016”。

### 第二步：建立 TCP 连接

浏览器让操作系统建立 TCP 连接：

```text
浏览器的临时端口 → 127.0.0.1:3016
```

浏览器自己也需要一个临时端口，连接可能类似：

```text
127.0.0.1:52348 → 127.0.0.1:3016
```

其中：

- `52348` 是浏览器临时使用的客户端端口
- `3016` 是 Vite 固定监听的服务端端口

操作系统查看自己的监听表，发现：

```text
TCP 3016 → Node/Vite 进程
```

于是把连接交给 Vite。

### 第三步：发送 HTTP 请求

TCP 连接建立后，浏览器发送类似这样的 HTTP 请求：

```http
GET / HTTP/1.1
Host: localhost:3016
```

意思是：

> 请把网站根路径 `/` 的内容给我。

Vite 收到请求后，返回项目中的 `index.html`。

内容的核心结构是：

```html
<body>
  <div id="root"></div>
  <script type="module" src="/src/main.tsx"></script>
</body>
```

注意，此时 HTML 里几乎没有真正的界面，只有一个空容器：

```html
<div id="root"></div>
```

以及前端程序入口：

```html
<script src="/src/main.tsx"></script>
```

### 第四步：浏览器继续请求 JavaScript 和 CSS

浏览器解析 `index.html` 后发现：

```text
我还需要 /src/main.tsx
```

于是继续向 Vite 请求：

```http
GET /src/main.tsx HTTP/1.1
Host: localhost:3016
```

`main.tsx` 又导入了：

```tsx
import './index.css'
import App from './App.tsx'
import RootLayout from './layouts/RootLayout.tsx'
```

所以浏览器和 Vite 会继续交换大量请求：

```text
浏览器 → 请求 main.tsx
浏览器 → 请求 App.tsx
浏览器 → 请求 RootLayout.tsx
浏览器 → 请求 index.css
浏览器 → 请求图标
浏览器 → 请求各个 React 组件
```

### 第五步：Vite 实时转换源代码

浏览器不能直接理解所有 TypeScript 和开发期 TSX 代码。

Vite 会在返回代码前进行转换：

```text
项目中的 TypeScript/TSX
          ↓
Vite 转换
          ↓
浏览器能执行的 JavaScript
```

例如 React 的 TSX：

```tsx
<App />
```

会被转换为浏览器可以运行的 JavaScript。

Vite 还会处理：

- TypeScript
- React TSX
- CSS
- Tailwind CSS
- 模块导入路径
- 开发时热更新

### 第六步：浏览器执行 React

浏览器下载 JavaScript 后，用自己的 JavaScript 引擎执行 `main.tsx`。

项目入口包含：

```tsx
createRoot(document.getElementById('root')!).render(
  <RootLayout>
    <App />
  </RootLayout>
)
```

它的意思是：

> 找到 HTML 中 id 为 `root` 的空容器，把整个 React 应用渲染进去。

原来的 HTML：

```html
<div id="root"></div>
```

经过 React 运行后，会在内部产生大量页面元素，概念上类似：

```html
<div id="root">
  <div class="页面布局">
    <aside>生成表单</aside>
    <section>生成历史</section>
    <main>笔记内容</main>
  </div>
</div>
```

### 第七步：浏览器绘制页面

浏览器最后依次完成：

```text
解析 HTML
    ↓
生成 DOM 元素树
    ↓
解析 CSS
    ↓
计算每个元素的位置和大小
    ↓
绘制文字、颜色、边框、图片
    ↓
显示到屏幕
```

于是你看到了 BiliNote 界面。

## 四、打开页面时后端参与了吗

显示基础界面主要是：

```text
浏览器 ↔ Vite 前端服务器
```

后端不一定参与最初的 HTML、JavaScript 和 CSS 下载。

因此即使后端没启动，你往往仍然可以打开：

```text
http://localhost:3016/
```

并看到页面。

但是前端启动后可能会进行后端健康检查，而且点击“生成笔记”、读取模型配置等功能必须请求后端。

所以：

```text
Vite 不运行
→ 浏览器拿不到页面代码
→ 网站打不开

后端不运行
→ 页面可能正常显示
→ 但生成笔记等功能无法使用
```

## 五、前端如何请求后端

前端代码通常不会让浏览器直接请求：

```text
http://127.0.0.1:8483
```

在当前开发配置下，它主要向自己所在的前端地址发送：

```text
http://localhost:3016/api/...
```

例如：

```text
POST http://localhost:3016/api/generate_note
```

Vite 看到路径以 `/api` 开头，就根据代理配置将请求转发到：

```text
http://127.0.0.1:8483/api/generate_note
```

数据流是：

```text
浏览器
  │ POST /api/generate_note
  ▼
Vite :3016
  │ 代理转发
  ▼
FastAPI :8483
```

这就是开发服务器的“代理”功能。

Vite 在这里有两个职责：

```text
Vite
├── 给浏览器提供 HTML、JavaScript、CSS
└── 把 /api 请求转发给后端 8483
```

## 六、点击“生成笔记”之后的数据流

你在页面里输入视频链接，然后点击“生成笔记”。

### 1. 浏览器里的 React 收集表单

React 整理出类似的数据：

```json
{
  "video_url": "https://www.bilibili.com/video/BV...",
  "model_name": "qwen-plus",
  "text_extraction_method": "ocr",
  "style": "详细"
}
```

### 2. 浏览器向前端地址发送请求

```text
POST localhost:3016/api/generate_note
```

### 3. Vite 转发给后端

```text
POST 127.0.0.1:8483/api/generate_note
```

### 4. FastAPI 匹配接口

FastAPI 根据请求路径找到对应的 Python 函数：

```text
/api/generate_note
        ↓
generate_note(...)
```

后端创建任务并返回任务 ID：

```json
{
  "task_id": "6cf090a2-e23d-4850-a5f6-9faa5ceec5dd"
}
```

### 5. 后端处理任务

后端工作线程继续处理：

```text
解析视频链接
    ↓
下载字幕、音频或视频
    ↓
OCR 或语音转写
    ↓
调用 AI 模型
    ↓
生成 Markdown
    ↓
写入 backend/note_results
```

### 6. 前端轮询进度

浏览器隔一段时间询问：

```text
GET /api/task_status/任务ID
```

请求依然经过 Vite 转发到后端。

后端可能返回：

```json
{
  "status": "TRANSCRIBING",
  "message": "正在转写文字"
}
```

完成后返回：

```json
{
  "status": "SUCCESS",
  "result": {
    "markdown": "最终笔记内容"
  }
}
```

### 7. React 更新页面

React 收到新数据后，更新自己的状态。

```text
旧状态：正在生成
新状态：生成完成
```

React 根据新状态重新计算页面，把笔记显示出来。它不会刷新整个网页，只更新发生变化的部分。

### 8. 保存生成历史

前端还会把任务历史写入浏览器 IndexedDB：

```text
http://localhost:3016
└── IndexedDB
    └── task-storage
```

所以以后再次打开相同的：

```text
http://localhost:3016
```

React 会从 IndexedDB 读取历史，再渲染到左侧列表。

如果打开的是：

```text
http://localhost:3015
```

浏览器会读取另一个 Origin 的 IndexedDB，所以不会看到 `3016` 的记录。

## 七、最关键的三个“运行位置”

很容易混淆的一点是：前端并不全部运行在 Vite 进程中。

准确划分如下：

| 部分 | 运行位置 | 主要职责 |
|---|---|---|
| Vite | Node.js 进程 | 提供前端文件、转换代码、代理 API |
| React | 浏览器内部 | 处理交互、构建页面、展示数据 |
| FastAPI | Python 进程 | 视频处理、AI 调用、保存结果 |

也就是说：

```text
“前端代码”React     → 主要运行在浏览器
“前端开发服务器”Vite → 运行在操作系统进程里
“后端程序”FastAPI    → 运行在另一个操作系统进程里
```

## 一句话总结

你执行两个启动命令后，操作系统中分别出现了 Python 后端进程和 Node/Vite 前端进程；浏览器访问 `localhost:3016` 时，先从 Vite 下载 HTML、JavaScript 和 CSS，然后在浏览器内部执行 React 并绘制界面；当页面需要处理视频时，请求通过 Vite 代理到 `8483` 上的 FastAPI 后端，后端完成计算并把 JSON 结果沿原路返回，React 再更新页面。
