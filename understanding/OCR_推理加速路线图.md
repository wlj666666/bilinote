# OCR 推理与高性能计算优化路线图

本文记录 BiliNote **画面字幕 OCR** 后续可以探索的提速方向。目标是在不同长度、横竖屏、字幕位置和画面文字密度的视频上缩短处理时间，同时保留字幕内容和时间轴。文中的速度数据是 **2026-10-01 本机测量或短片段抽样**，不是未来改动的性能保证。

## 1. 目前的数据流

```mermaid
flowchart LR
    A[视频文件] --> B[FFmpeg 完整性校验]
    B --> C[PyAV 第一次解码：每 2 秒取一帧]
    C --> D[RapidOCR 全画面：检测 → 方向分类 → 识别]
    D --> E[分析时间窗口，定位字幕区域]
    E --> F[PyAV 第二次解码：默认每秒取 5 帧]
    F --> G[按字幕区域裁剪画面]
    G --> H[RapidOCR 字幕区域：检测 → 方向分类 → 识别]
    H --> I[过滤、合并字幕、质量检查]
    I --> J[把原文交给总结模型]
```

- 实现入口：[字幕提取流程](backend/app/services/hard_subtitle_extractor.py)、[OCR 引擎](backend/app/ocr/ocr_engine.py)、[字幕位置跟踪](backend/app/ocr/subtitle_tracker.py)。
- 两次扫描都会顺序解码视频；OCR 模型运行在 ONNX Runtime CUDA Execution Provider 上，PyAV 解码、画面裁剪及部分 OCR 前后处理仍由 CPU 完成。GPU 的“3D”或“Video Decode”曲线不能单独判断 OCR 推理是否使用 CUDA，任务诊断中的 `runtime.providers` 更直接。
- 以下优化主要作用于 **C～I**。下载、FFmpeg 校验及后续总结另行计时，避免把它们算作 OCR 推理收益。

## 2. 已测得的基线

| 范围 | 结果 | 对优化的提示 |
| --- | --- | --- |
| 一条约 56 分钟、768×480 的视频 | OCR 约 22.2 分钟：定位约 7.5 分钟，逐帧提取约 14.7 分钟 | 两遍 OCR 都值得优化，第二遍优先级更高 |
| 同一视频的完整 FFmpeg 解码校验 | 约 9 秒 | 目前不是主要耗时 |
| 三条视频各取 3 张全画面帧，共 9 帧 | OCR 合计约 2.81 秒：检测 0.68、方向分类 0.50、文字识别 1.60 秒；文字框中位数 58 | 全画面识别了大量画面文字，文字识别占比最高 |
| 同样 9 张帧的字幕区域裁剪 | OCR 合计约 0.64 秒：检测 0.19、分类 0.17、识别 0.26 秒；文字框中位数 3 | 缩小处理范围很有价值，但仍需要发现字幕位置变化 |
| 三条视频各取四段、每段 10 秒的相邻 5 fps 字幕画面 | 原尺寸裁剪图逐像素完全相同约 14%～25%；缩小后的画面约 73%～87% 几乎不变 | 严格重复帧复用有保守收益；近似帧跳过需防漏字 |

测试环境为 RTX 5060 Laptop GPU（约 8 GB 显存）、ONNX Runtime GPU 1.21.0、RapidOCR 3.9.2，`OCR_DEVICE=cuda`、`OCR_FPS=5`。重复帧比例只统计相同字幕裁剪区域内的相邻可用采样帧；“几乎不变”指缩到 320×48 灰度图后，两帧差值大于 10 的像素少于 0.1%。这个低分辨率指标只用于寻找优化机会，不能作为实际跳过 OCR 的判据。

这些短测只用于确定探索顺序。不同视频的画面文字数量、分辨率、字幕持续时间和字幕区域大小都可能改变收益。

### 已尝试的直接参数调整

在三条视频抽取的 9 张全画面帧上做过短测；下表的“文字变化”表示相对原设置的识别结果出现差异，需要进一步确认原因和质量影响。

| 调整 | 短测结果 | 当前判断 |
| --- | --- | --- |
| 文字识别 batch 从 6 提到 12 | 9 帧合计 3.382 → 3.326 秒，4 帧文字不同 | 收益约 2%，不适合直接设为全局默认 |
| batch 提到 24 | 9 帧合计 3.89 秒，5 帧文字不同 | 更慢 |
| CUDA TF32 从关闭改为开启 | 全画面 3.18 → 3.02 秒，字幕裁剪 0.702 → 0.758 秒；全画面有文字差异 | 收益不稳定，不能只看全画面推理速度 |
| 关闭文字方向分类 | 全画面 3.277 → 2.534 秒，裁剪 0.721 → 0.493 秒；分别有 7 帧、1 帧文字不同 | 有明显速度空间，但不能无条件关闭 |

## 3. 按数据流位置排列的可探索方向

### 方向 A：复用完全相同画面的 OCR 结果

- **对应位置：**G → H，裁剪后、调用 OCR 前。
- **原理：**若当前字幕区域与上一采样帧的原始像素、尺寸和裁剪位置都完全相同，就沿用上一帧的识别框及文字，再给它当前帧的时间戳。相同输入不需要再次调用模型。
- **涉及技术栈：**PyAV、NumPy 图像比较、RapidOCR、字幕时间轴合并。
- **验证重点：**与原流程逐条比较字幕文字、时间和质量诊断；确认跨字幕窗口、裁剪区域改变、空白帧和不确定区域时正确失效。抽样中的完全相同帧比例是潜在省调用量，**不是整片提速百分比**。
- **顺序：**最先做；不依赖某个视频的字幕位置或相似度阈值。

### 方向 B：用廉价的画面变化检测减少近重复推理

- **对应位置：**F → G → H，第二次采样后、字幕区域 OCR 前。
- **原理：**先用快速图像比较判断字幕区域是否可能发生文字变化；明显不变时复用结果，变化或判断不清时照常 OCR，并定期强制复查。字幕切换附近可以补查前后帧来保住时间边界。
- **涉及技术栈：**OpenCV、NumPy、时间序列状态机、RapidOCR。
- **验证重点：**单字/数字变化、短暂字幕、动画背景、光标闪烁、渐变、压缩噪声和多行字幕。缩小图的“近似相同”不能直接当作可跳过 OCR 的证据；必须在原尺寸文字区域验证。需要多类视频的人工参考原文。
- **顺序：**完成方向 A 后研究；收益潜力大，误判风险也更高。

### 方向 C：分层完成全画面字幕定位

- **对应位置：**C → D → E，第一次全画面扫描。
- **原理：**先用较便宜的文字检测找候选位置，优先对可能的字幕带做方向分类和文字识别。已经确认稳定区域时，可以减少其他位置的完整识字，但仍定期扫描全画面，以发现字幕移位或第二套真实字幕布局。
- **涉及技术栈：**RapidOCR 的检测、分类和识别子模型，OpenCV，`subtitle_tracker.py` 的跨时间窗口跟踪。
- **验证重点：**录屏里的代码、菜单和状态栏，竖屏字幕，多位置字幕，片头没有字幕、片中才出现字幕的情形。必须保留“不确定”结果，不能为了加速把竞争文字强行当成字幕。
- **顺序：**优先于换推理框架；当前全画面中位数约 58 个文字框，识别无关文字有明确成本。

### 方向 D：把多帧组织成批次，并控制输入形状

- **对应位置：**G → H，裁剪后的 GPU 推理。
- **原理：**把尺寸相近的多帧字幕区域暂存成一个小批次，让 GPU 一次处理更多输入，减少频繁启动很小计算任务的开销。宽高差异大的画面先分组或填充，处理完再按原视频时间顺序还原结果。
- **涉及技术栈：**ONNX 模型动态 batch、ONNX Runtime CUDA Execution Provider、CUDA/cuDNN、NumPy、RapidOCR 检测后处理。
- **实现边界：**当前 RapidOCR 的外层接口一次接收一张图；它只对**同一帧内**的文字框做批量分类/识别（现有 batch 为 6）。跨帧批处理需要改造检测与后处理流程，不能仅调大 `rec_batch_num`。
- **验证重点：**批量大小、填充浪费、8 GB 显存峰值、文字与时间戳一一对应、不同分辨率和字幕区域尺寸；同时测冷启动、稳定运行与整片耗时。

### 方向 E：让 CPU 准备下一批画面与 GPU 推理重叠

- **对应位置：**C/D 和 F/G/H，解码、图像预处理与模型推理之间。
- **原理：**当前流程基本是“取帧 → 裁剪 → 推理 → 再取下一帧”。用有容量上限的队列提前解码/裁剪下一批画面，可以在 GPU 推理当前批时让 CPU 准备后续输入，减少彼此等待。若设备拷贝占比高，再评估 I/O Binding，把输入输出缓冲区安排在 GPU 上。
- **涉及技术栈：**PyAV、Python 线程或进程与有界队列、ONNX Runtime I/O Binding、CUDA 内存/流。
- **验证重点：**用阶段计时证明确实存在可重叠的 CPU 与 GPU 工作；限制队列内存，保持时间顺序和异常退出清理。当前 OCR 后处理需要把识别结果取回 CPU，I/O Binding 不能消除全部拷贝。[ONNX Runtime I/O Binding 说明](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html)。

### 方向 F：试验 FP16、TensorRT 与引擎缓存

- **对应位置：**D/H，三个 ONNX 模型的 GPU 计算。
- **原理：**FP16 使用更低精度计算和更少显存；TensorRT 可针对 GPU 和模型生成优化后的执行引擎，并把构建结果缓存下来。对于尺寸多变的 OCR 输入，需先设置合适的形状范围，否则可能反复构建引擎。
- **涉及技术栈：**ONNX Runtime FP16 模型转换或 TensorRT Execution Provider、TensorRT、CUDA、cuDNN、动态形状 profile、引擎缓存。[ONNX Runtime TensorRT 选项](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html)、[FP16 模型转换](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html)。
- **当前环境：**ONNX Runtime 列出了 TensorRT Execution Provider，但本机 Python 环境及系统库中没有找到 TensorRT 运行库；不能据 provider 列表认定已经能使用 TensorRT。
- **验证重点：**安装与首次构建成本、缓存命中率、显存峰值、全片耗时、文字和时间轴差异。模型、ONNX Runtime、TensorRT 或显卡变化时需要使对应引擎缓存失效。低精度可能改变边缘文字识别，不能只比较速度。[NVIDIA 精度说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/accuracy-considerations.html)。

### 方向 G：固定形状后评估 CUDA Graph

- **对应位置：**D/H，重复执行的 GPU 模型调用。
- **原理：**把同形状、同内存地址的 GPU 计算过程预先记录，后续直接重放，减少每次从 CPU 发出许多小指令的开销。当前 OCR 输入宽高动态变化，必须先解决形状分组和 GPU 内存绑定。
- **涉及技术栈：**ONNX Runtime CUDA Graph、I/O Binding、固定缓冲区、方向 D 的形状分组。[ONNX Runtime CUDA 文档](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。
- **验证重点：**图捕获/预热成本、动态输入形状覆盖率、显存占用及整片收益。这不是目前可直接打开的通用加速开关。

### 方向 H：有条件地调整方向分类、精度和量化

- **对应位置：**D/H，OCR 子模型的执行策略。
- **原理：**对可靠的水平字幕候选，可探索跳过方向分类并在不确定时恢复；也可评估 TF32、混合精度或 INT8，让部分计算更快。INT8 需要代表性画面做校准，把浮点数映射到较小的整数范围。
- **涉及技术栈：**RapidOCR `use_cls`、ONNX Runtime CUDA 选项、FP16/TF32、TensorRT INT8 与校准数据。[ONNX Runtime 量化说明](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)。
- **验证重点：**短测已显示关闭分类有速度收益但文字会变化；TF32 与简单增大识别 batch 的收益不稳定。要按字幕样本、视频类型和完整任务结果评估，不能把一次微基准的最快配置设为全局默认。
- **顺序：**在建立多视频质量基准后进行；INT8 最后考虑。

### 当前低优先级：只优化视频解码

- **对应位置：**B/C/F，FFmpeg 校验与 PyAV 解码。
- **原理与技术栈：**FFmpeg、PyAV、可选 NVDEC 硬件解码。硬解可以减少 CPU 解码工作，但不会减少每帧 OCR 的检测、分类和识别次数。
- **判断依据：**本次 56 分钟视频的完整性校验约 9 秒；短片段里 OCR 调用约占处理时间的九成。先验证以上 OCR 方向，再决定是否值得引入硬解及额外的视频格式兼容工作。

## 4. 推荐实施顺序和验收办法

1. **先建立统一基准：**分开记录解码、检测、方向分类、识别、后处理、GPU/CPU 拷贝和总结耗时；分别测首次运行与模型/引擎缓存命中后的运行。记录显存峰值、CPU 使用、实际 Execution Providers。
2. **先实现方向 A：**严格相同帧复用。用完整视频比较文字、分段开始/结束时间、`quality_status`、`text_gaps` 和 `missing_region_seconds`，再确认整片实际提速。
3. **再探索 B、C：**优先减少没有必要的模型调用及无关文字识别。测试横屏、竖屏、录屏、多字幕位置、片尾卡、短字幕、单字符与数字变化，人工检查优化前后差异。
4. **之后试 D、E：**用模型分阶段时间和整片吞吐量决定批大小、形状分组及流水线深度。GPU 利用率升高不等于任务完成得更快，以整片耗时和原文质量为准。
5. **最后试 F～H：**建立独立的推理配置、模型版本和缓存签名；任何低精度或新执行提供者都需多视频逐字对照和故障回退验证。

所有探索都以**跨视频实测**判断，不按某个 BV 号或固定视频时长分支。减少 OCR 调用、提高单次推理效率、降低 CPU/GPU 等待应分别计时，这样才能知道每一步实际改善了数据流的哪一段。
