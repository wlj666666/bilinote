## 4. “朴素部署法”的核心思路与挑战 [原片 @ 03:58](https://www.bilibili.com/video/BV1XKei6CEua?t=238)

**核心思路**：把服务器当作另一台电脑，尽可能地复用本地的运行方式和已有知识来部署。

**项目在本地运行的方式**：
- 前端通过 `npm run dev` 监听 **3000** 端口。
- 后端通过 `fastapi dev` (背后是 Uvicorn) 监听 **8000** 端口。
- 浏览器访问前端页面，页面内的 JS 脚本通过 `fetch` 请求后端接口。

**服务器上的部署方案**：
- 前端仍通过 Nginx 在 **80** 端口提供静态资源。
- 后端与本地一样，通过 Uvicorn 在 **8000** 端口提供服务。

**已知与挑战分析**：虽然很多知识已掌握，但直接上手会遇到四类挑战，归纳为四件事：

| 挑战 | 描述 | 解决路径 |
| :--- | :--- | :--- |
| **1. 配置文件** | 前端 `.env.local` 不进 Git，服务器上需手动创建；后端中间件 `localhost` 地址写死在代码里，线上会水土不服。 | 将地址等变量抽取到 `.env` 配置文件。 |
| **2. 启动命令** | `fastapi dev` 仅接受本机访问，不适合线上。 | 改用 `fastapi run`。 |
| **3. 后台常驻** | 后端程序在终端窗口关闭后即终止。 | 使用 `nohup` 等命令让进程在后台持续运行。 |
| **4. 防火墙** | 云平台安全组默认不开放 8000 端口。 | 手动在防火墙放行 8000 端口。 |

## 5. 配置文件（.env）详解与改造 [原片 @ 11:47](https://www.bilibili.com/video/BV1XKei6CEua?t=707)

配置文件是为了将代码与环境相关的变量（如 API Key、数据库密码、不同环境的地址）分离，让同一份代码通过不同配置服务不同环境。

**项目中的改造步骤**：

1.  **提交历史代码**：先提交上一节“实现历史记录”的代码，形成一个新的 commit，确保工作区干净。

2.  **创建后端配置文件**：
    - 在后端目录下创建 `.env` 文件，写入一行配置：`ALLOWED_ORIGINS=http://你的服务器IP`。
    - **注意**：线上前端由 Nginx 在 80 端口提供，而 80 是 HTTP 默认端口，请求头中不含端口号，因此这里的地址**不要写 80 端口**。

3.  **让代码读取配置**：
    - 安装 `python-dotenv` 库，并将其记录到 `requirements.txt`。
    - 修改 `main.py`，引入相关库并通过 `os.getenv("ALLOWED_ORIGINS")` 读取变量，替换掉中间件里写死的地址。

4.  **配置文件命名与进 Git 的策略**：
    - **前端**：Next.js 根据运行环境自动寻找，开发时用 `.env.local`，构建时会优先找 `.env.production`。
    - **后端**：框架约定默认读取 `.env` 文件。
    - **敏感性**：`.env` 等实际生效的配置文件包含敏感信息且与环境相关，**不能**提交到 Git。
    - **示例文件 (`.env.example`)**：为前后端分别创建 `.env.example` 文件，仅保留配置项的 Key 和示例 Value，用于展示配置格式。该文件**可以**进入 Git。
    - **`.gitignore` 调整**：因 `.gitignore` 忽略了所有 `.env*` 文件，需在其中添加 `!.env.example` 使示例文件不被忽略。

完成所有修改后，将代码提交并推送到 GitHub。

## 6. 服务器端实操：环境搭建与项目启动 [原片 @ 25:54](https://www.bilibili.com/video/BV1XKei6CEua?t=1554)

登录服务器，拉取最新代码到 `zero-to-tech` 目录。

**1. 搭建后端 Python 环境**：
- 检查 Python 版本，确保在 3.10 以上。
- 进入 `backend` 目录，创建虚拟环境：`python3 -m venv .venv`。
- 激活虚拟环境：`source .venv/bin/activate`。
- 根据 `requirements.txt` 安装项目依赖：`pip install -r requirements.txt`。

**2. 准备前后端配置文件**：
- **前端**：在项目根目录（`frontend`），基于 `.env.example` 复制出 `.env.production`，并将其中的后端地址修改为 `http://182.254.229.21:8000`（使用你的服务器 IP）。
- **后端**：在 `backend` 目录下，基于 `.env.example` 复制出 `.env`，并写入前端地址 `http://182.254.229.21`（使用你的服务器 IP，无端口号）。

**3. 构建与启动项目**：
- **启动前端**：回到项目根目录，执行 `npm install` 安装新依赖，然后执行 `npm run build` 构建生产版本。构建时控制台会输出 `environment: .env.production`，表示使用了正确的配置文件。前端静态文件由 Nginx 代理。
- **启动后端**：进入 `backend` 目录，执行 `fastapi run`。该命令默认监听 `0.0.0.0:8000`，接受来自外部的连接，这与 `fastapi dev` 仅监听 `127.0.0.1` 截然不同。

**4. 初步验证**：
- 新开一个终端窗口登录同一台服务器。
- 执行 `curl localhost:8000`，若能返回 JSON 数据，则说明服务器本地请求后端已通。
- 检查 `backend` 目录下是否已自动创建 `history.db` 数据库文件，确认数据库已初始化。

## 7. 防火墙配置与公网验证 [原片 @ 39:33](https://www.bilibili.com/video/BV1XKei6CEua?t=2373)

尽管服务器本地运行正常，但浏览器访问仍会报错 `failed to fetch`，原因是云平台防火墙未开放 8000 端口。

- **解决方案**：在云平台控制台的“防火墙”或“安全组”设置中，新增一条规则，放行 8000 端口。
- **验证结果**：刷新网页，点击“分析”按钮成功返回结果，历史记录功能也可正常使用。使用 Chrome 和 Safari 等不同浏览器测试，会话（Session）功能正常，互不干扰。

至此，项目已成功上线，并可将链接分享给他人。

## 8. 后台常驻：使用 `nohup` 保持服务运行 [原片 @ 42:06](https://www.bilibili.com/video/BV1XKei6CEua?t=2526)

当关闭运行 `fastapi run` 的终端窗口后，后端程序随即终止，网站分析功能再次报错。

**原因**：Uvicorn 作为前台进程寄生在 SSH 会话里，会话结束，进程便终止。

**解决方案**：使用一条组合命令让进程在后台常驻。需要在已激活虚拟环境的 `backend` 目录下执行：

```bash
nohup .venv/bin/fastapi run main.py > backend.log 2>&1 &
```

**命令分解**：
- `nohup` (no hang up)：让进程在 SSH 会话断开后继续存活。
- `&`：将命令放到后台运行，不占用终端。
- `> backend.log`：将程序的标准输出重定向到 `backend.log` 文件。
- `2>&1`：将标准错误输出也一并重定向到 `backend.log`，方便后续排查问题。

执行后，即使关闭本地终端，网站功能依然正常，实现了服务常驻。

## 10. 当前部署方案的缺点与下节预告 [原片 @ 48:46](https://www.bilibili.com/video/BV1XKei6CEua?t=2926)

目前的“朴素”部署方案虽然可用，但存在三个主要缺点，这也引出了下节课的内容：

1.  **后端服务脆弱**：
    - 不会崩溃自愈或开机自启。服务器一旦重启，后端服务不会自动起来。
    - 管理完全依赖手工，更新或重启代码麻烦，查看状态和日志不便。
2.  **8000 端口裸奔**：
    - 缺少日志记录，无法审计。
    - 没有加密，后续配置 HTTPS 的 SSL 证书在 Nginx 上，保护不了该端口。
    - 缺少限流和安全防护能力，增加了风险。
3.  **跨域（CORS）困扰**：
    - 前后端端口不同导致的跨源问题虽已解决，但在后续上域名、上 HTTPS 时，可能会带来新的困扰。

**下节（7.2）改进方向**：
- 使用 `systemd` 取代 `nohup`，实现开机自启和崩溃自愈，并更方便地查看状态和日志。
- 使用 Nginx 反向代理，将后端 API 也接入 80 端口，实现前后端同源，简化配置，一举解决多个问题。

课程重点讲解了如何处理开发与生产环境的差异，其中**配置文件（`.env`）的抽象与管理**是重中之重。通过将前端 API 地址和后端 CORS 白名单等环境变量抽离，并用 `.env.example` 文件作为无敏感信息的模板进行 Git 版本管理，项目代码与配置得以解耦。随后，在服务器上完整实践了从 Python 环境搭建、依赖安装、配置文件创建到使用 `fastapi run` 启动后端，并配合 `nohup` 和 `&` 实现进程后台常驻的全过程。最后，通过配置云防火墙放行端口，项目成功面向公网提供服务。

课程最后并未止步于“能用”，而是清晰地指出了当前方案的三个核心缺陷：服务脆弱无守护、8000 端口安全性和可靠性不足、以及潜在的跨域问题，并预告了下一节将使用 `systemd` 和 Nginx 反向代理来解决这些问题，完成从“有”到“好”的演进。
