## 目标与背景：为何要重构存储层 [原片 @ 00:00](https://www.bilibili.com/video/BV1s94X6cEvx?t=0)
- 上一节已学习数据库基础知识：建表、增删改查、问号防注入、索引。
- 但 `zero-to-tech` 项目至今未使用数据库，仍用上上节自写的 `history.json` 文件承担存储职责。
- 本节目标：将 `history.json` 替换为 SQLite 数据库，**仅改动存储层**。
- Python 代码会修改较多，但**不破坏接口约定**（如 `/api/history` 的请求/响应格式），因此前端无需变更。

## 代码分层分析：接口层、业务层、存储层 [原片 @ 01:16](https://www.bilibili.com/video/BV1s94X6cEvx?t=76)
`main.py` 当前虽短（几十行），但混杂三种职责：
- **接口层**：`@app.get` / `@app.post` 装饰的函数，负责接收请求、返回响应（如 `/api/history`）。
- **业务层**：计算情感分、拼音、拼装记录等逻辑（如 `analyze_text` 函数内操作）。
- **存储层**：所有与“存哪、怎么存、怎么取”相关的代码，包括：
  - `import json`
  - `HISTORY_FILE` 常量
  - `load_history()` 和 `save_record()` 函数
  - 接口函数中直接读取 `history.json` 并排序切片的三行代码（如 `/api/history` 中的 `records = json.load(...)`, `records[::-1][:2]`）

> 注：当前职责不清晰 —— 存储逻辑（如排序切片）写在接口函数内，导致后续更换存储时需侵入接口层修改，违背分层原则。

## 整体重构策略：功能不变、只挪位置、分步验证 [原片 @ 03:43](https://www.bilibili.com/video/BV1s94X6cEvx?t=223)
- **重构定义**：业内标准是“在不改变外部可观测行为的前提下，调整代码内部结构”。行为变了就不叫重构。
- **核心纪律**：重构期间**功能一点都不能变**；重构完必须运行验证，任何差异即说明重构出错。
- **两步走方案**：
  1. **搬家**：将全部存储层代码原样搬入新文件 `storage.py`，**仍用 `history.json`**，`main.py` 仅做 import 和调用适配。目标：验证“仅移动位置”是否成功。
  2. **装修**：将 `storage.py` 内部实现替换为 SQLite，`main.py` 几乎不动。目标：更换实现，行为可变（如新增 `id` 字段）。
- **为何必须分两步？**  
  搬错（结构问题）和改错（逻辑问题）是两类错误。分步可锁定问题范围：搬家后验证通过 → 说明结构正确；装修后出错 → 必定是 SQLite 实现问题。

## 第一步：搬家——提取 storage.py [原片 @ 07:02](https://www.bilibili.com/video/BV1s94X6cEvx?t=422)
- **操作**：
  - 在 `backend/` 目录下新建 `storage.py`。
  - 将 `main.py` 中以下内容**剪切**（非复制）至 `storage.py`：
    - `import json`
    - `HISTORY_FILE = "history.json"`
    - `load_history()` 函数
    - `save_record()` 函数
    - `/api/history` 接口函数中读取、排序、切片的三行代码 → 提取为新函数 `get_history(limit: int)`（暂保留原逻辑，`limit` 参数先设为硬编码，后续再解耦）。
- **main.py 同步修改**：
  - 删除被剪切的代码。
  - 添加 `from storage import save_record, get_history, init_db`（`init_db` 为后续建表预留）。
  - 将 `/api/history` 接口函数中被剪切的三行替换为 `return get_history(10)`。
- **验证**：重启服务，确认 `/api/history` 返回数据、`history.json` 文件内容更新，与搬家前完全一致。

## 第二步：职责再梳理——LIMIT 决定权上移 [原片 @ 17:00](https://www.bilibili.com/video/BV1s94X6cEvx?t=1020)
- **问题发现**：`storage.py` 中 `get_history(limit: int)` 的 `limit` 值（如 `10`）本质是**前端展示需求**（页面显示几条），不属于存储层职责。
- **存储层应有职责**：只负责“按要求取指定数量”，**不决定数量本身**。
- **解决方案**：
  - `storage.py` 中 `get_history` 函数签名改为 `get_history(limit: int)`，强制调用方传参。
  - `main.py` 中 `/api/history` 接口调用 `get_history(10)`，将“取10条”的决策权交还给接口层（未来可由前端传参控制）。
- **验证**：行为未变（仍返回10条），但职责归属更清晰。此调整也属重构范畴（调整职责边界，非仅移动代码）。

## 第三步：装修——SQLite 六处改造详解 [原片 @ 22:46](https://www.bilibili.com/video/BV1s94X6cEvx?t=1366)
`storage.py` 改造共 6 处，全部围绕 SQLite 替代 JSON：

| 序号 | 位置 | 修改内容 | 关键说明 |
|------|------|----------|----------|
| 1 | 顶部 import | `import json` → `import sqlite3` | 不再操作文件系统 |
| 2 | 连接管理 | 删除 `HISTORY_FILE`；新增 `get_conn()` 函数 | 返回带 `row_factory=sqlite3.Row` 的连接，使查询结果支持字段名访问（如 `row['created_at']`） |
| 3 | 建表逻辑 | 新增 `init_db()` 函数，内含 `CREATE TABLE IF NOT EXISTS history (...)` | 表结构含 `id INTEGER PRIMARY KEY AUTOINCREMENT`, `text TEXT`, `sentiment REAL`, `pinyin TEXT`, `created_at TEXT`；`IF NOT EXISTS` 避免重复建表 |
| 4 | `save_record` | 替换为 `INSERT INTO history (text, sentiment, pinyin, created_at) VALUES (?, ?, ?, ?)` | 使用 `?` 占位符防 SQL 注入；时间戳由 Python 传入（非 SQLite `datetime('now')`） |
| 5 | `get_history` | 替换为 `SELECT * FROM history ORDER BY created_at DESC LIMIT ?` + `fetchall()` + 字段转换 | `LIMIT ?` 对应参数；`fetchall()` 返回列表；循环将 `sqlite3.Row` 转为字典 |
| 6 | `load_history` | **直接删除** | 此函数仅用于全量读取 JSON，SQLite 版本无对应需求 |

- **main.py 同步修改**：在 `import` 后添加 `init_db()` 调用，确保启动时建表。
- **验证**：重启服务 → 分析文本 → 访问 `/api/history` → 确认返回数据；检查项目目录出现 `history.db`；用数据库可视化工具确认表存在、数据写入、`id` 字段自增。

## 善后事项：.gitignore、history.json 删除、ORM 简介、索引实践 [原片 @ 35:17](https://www.bilibili.com/video/BV1s94X6cEvx?t=2117)
- **.gitignore**：添加 `backend/*.db`，防止 `history.db` 被 Git 追踪（数据属运行时产物，非代码）。
- **history.json**：直接删除。项目未上线，历史数据不迁移；强调真实项目中数据迁移是高要求专业工作，不可忽略。
- **ORM 简介**：
  - ORM（Object-Relational Mapping）如 FastAPI 官方推荐的 `SQLModel`，允许用 Python 语法（非手写 SQL）操作数据库。
  - 本质仍是生成 SQL 交给数据库执行，ORM 框架负责转换。
  - 本项目未采用，因直接 SQL 更透明、适合教学；ORM 是可选方案，非必需。
- **索引实践**：
  - `history` 表中 `created_at` 字段常用于 `ORDER BY`，适合建索引。
  - 添加 `CREATE INDEX IF NOT EXISTS idx_history_created ON history(created_at)` 到 `init_db()` 中。
  - 强调：索引非越多越好；仅对高频筛选/排序字段建立；小数据量（如几十条）建索引无性能收益，甚至可能拖慢写入。

## 本节小结与下一节预告 [原片 @ 44:33](https://www.bilibili.com/video/BV1s94X6cEvx?t=2673)
- **本节完成**：
  - `main.py` 分层清晰化，独立出 `storage.py`。
  - 存储层完成从 `history.json` 到 `history.db` 的迁移。
  - `LIMIT` 决策权移交接口层，职责进一步解耦。
- **现状**：所有用户的历史记录仍混存于同一张 `history` 表中，`/api/history` 返回全部记录。
- **下一节预告**：引入**会话（Session）**，使服务器能识别不同浏览器请求，为每条记录打上用户标识，实现“用户只能查看自己的历史记录”。
