## 数据库的必要性与演进背景 [原片 @ 00:00](https://www.bilibili.com/video/BV1AR8U6REzY?t=0)

- 视频承接上一节“数据库前传”，该节中自行用文件实现了一个简易存储系统，能存能读但存在严重缺陷：
  - 存一条记录需重写整份文件；
  - 多人同时写会相互覆盖；
  - 写一半崩溃会导致数据全坏；
  - 这些问题并非项目特有，而是**任何人用文件存储不断增长的结构化数据时都会不可避免遭遇的共性问题**。
- 因信息存储是人类普遍需求，此类共性问题必有成熟解法——即**数据库**。
- 数据库诞生早于互联网：首个计算机数据库诞生于 **1961 年**，而互联网诞生于 **1969 年**，数据库已发展数十年，形成“百花齐放、百家争鸣”格局。
- 常见数据库举例：MySQL、PostgreSQL、SQLite、MongoDB 等。

## 数据库分类：关系型 vs 非关系型 [原片 @ 02:18](https://www.bilibili.com/video/BV1AR8U6REzY?t=138)

- 分类维度之一：**数据模型**。
- 区分依据：所存数据的形态。
  - **结构化数据**：有固定字段，每行整齐对应表格，如 CSV 或关系表。最适合**关系型数据库（Relational Database）**。
  - **半结构化数据**：有松散结构，允许每条记录字段不完全一致，典型代表是 JSON。适合**非关系型中的文档型数据库（如 MongoDB）**。
  - **非结构化数据**：无行列结构，如纯文本、图片、视频。一般不塞入数据库，而是存入**对象存储（Object Storage）**；对象存储属非关系型，但通常不被称作“数据库”。
- 关系型数据库强调数据规范，使用 **SQL（Structured Query Language，常读作 “sequel”）** 作为通用操作语言。
- 非关系型数据库统称 **NoSQL**，意为 **Not Only SQL**，对数据格式要求更松散、灵活。
- 两类是为不同场景而生的工具，“不存在谁更高级”。

## 数据库分类：嵌入式 vs 服务式 [原片 @ 04:27](https://www.bilibili.com/video/BV1AR8U6REzY?t=267)

- 分类维度之二：**服务方式**。
- **服务式数据库**（如 MySQL、PostgreSQL）：
  - 是独立、常驻的程序进程；
  - 需安装、启动，监听固定端口（MySQL 默认 **3306**，PostgreSQL 默认 **5432**）；
  - 支持多应用并发连接、精细权限控制、高并发任务；
  - 主流生产环境后端普遍采用。
- **嵌入式数据库**（如 SQLite）：
  - 本质就是一个文件（如 `.db` 文件），无需单独启动、不占端口；
  - Python 标准库自带 `sqlite3` 模块，安装 Python 即可用，`import sqlite3` 即可；
  - 轻量但强大：手机中普遍存在数十个 SQLite 文件（如微信聊天记录、浏览器历史）。

## 文字实验室的技术选型依据 [原片 @ 05:50](https://www.bilibili.com/video/BV1AR8U6REzY?t=350)

- 选型从需求出发：

  - **规模与场景**：文字实验室是小项目，无需多应用共享、无高并发压力 → 无需养一个常驻服务 → **嵌入式模式更合适**。

- 最终选定 **SQLite**，理由：
  - DuckDB 更偏数据分析场景，而文字实验室以日常增删改查为主；
  - SQLite 是 Python 标准库自带，零安装、零配置、几乎零维护。

## SQLite 入门实践：连接与 cursor [原片 @ 06:59](https://www.bilibili.com/video/BV1AR8U6REzY?t=419)

- 演示环境：Python REPL（交互式命令行）。
- 创建测试数据库 `test.db`（位于家目录）：
  ```python
  import sqlite3
  conn = sqlite3.connect("test.db")
  cur = conn.cursor()
  ```
- 三行代码为固定搭配：
  - `import sqlite3`：导入模块；
  - `sqlite3.connect("test.db")`：连接文件，若不存在则自动创建；
  - `conn.cursor()`：获取 cursor 对象，后续所有数据库操作均需通过它执行。
- 执行后，家目录下即生成 `test.db` 文件 —— 这正是 SQLite 的工作方式：**一个数据库即一个文件**。

## SQL 基础语法与 SQLite 方言特点 [原片 @ 09:03](https://www.bilibili.com/video/BV1AR8U6REzY?t=543)

- 所有关系型数据库均可通过 SQL 操作，但各数据库支持的语法细节存在差异，称为 **SQL 方言**。
- SQLite 的 SQL 方言以**精简**著称，其核心数据类型仅三种：
  - `INTEGER`（整数）
  - `REAL`（浮点数）
  - `TEXT`（文本）
- SQLite **没有专用的日期/时间类型或布尔类型**：
  - 时间用 `TEXT` 存储（如 `"2024-05-20 15:30:00"`）；
  - 布尔值用 `0`（False）和 `1`（True）代替。
- 正因精简，SQLite 才能嵌入手机、成为单文件数据库。

## 建表语句详解（含主键、自增、TEXT 存时间） [原片 @ 11:13](https://www.bilibili.com/video/BV1AR8U6REzY?t=673)

- 以电影信息表 `films` 为例，字段包括：名称（title）、语言（language）、上映时间（release_date）、创建时间（created_at）。
- SQLite 建表语句：
  ```sql
  CREATE TABLE films (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT,
      language TEXT,
      release_date TEXT,
      created_at TEXT
  );
  ```
- 关键点说明：
  - `id INTEGER PRIMARY KEY AUTOINCREMENT`：
    - `PRIMARY KEY`：声明主键，自动创建索引；
    - `AUTOINCREMENT`：自增字段，插入时无需指定值，数据库自动递增；
    - 主键用于**唯一标识一行数据**（因 title、language 等字段均可能重复）。
  - 其余字段均为 `TEXT` 类型，符合 SQLite 类型系统限制。

## INSERT 与事务 commit 的必要性 [原片 @ 14:22](https://www.bilibili.com/video/BV1AR8U6REzY?t=862)

- 插入单条电影《肖申克的救赎》示例：
  ```python
  cur.execute(
      "INSERT INTO films (title, language, release_date, created_at) "
      "VALUES (?, ?, ?, datetime('now'))",
      ("肖申克的救赎", "英语", "1994-09-23")
  )
  conn.commit()
  ```
- 注意事项：
  - 文本值（如 `"肖申克的救赎"`）需用**单引号包裹**；
  - `datetime('now')` 是 SQLite 函数，**无引号**，表示插入当前时间；
  - `id` 字段未显式赋值，因已设 `AUTOINCREMENT`，由数据库自动填充；
  - 必须调用 `conn.commit()`：此为**提交事务**，此前 `execute` 的操作仅在内存/缓存中，未真正写入磁盘。
- `commit` 的意义：
  - 确保多个关联操作（如“销售表+1”且“库存表−1”）**原子性执行**：要么全部成功，要么全部失败；
  - 避免中间状态被其他查询读取导致数据不一致；
  - 支持回滚（`rollback`）以撤销未提交的操作。

## SELECT 查询与 WHERE 条件表达式 [原片 @ 18:22](https://www.bilibili.com/video/BV1AR8U6REzY?t=1102)

- 基础查询三要素：`SELECT`（查哪些字段）、`FROM`（从哪张表）、`WHERE`（按什么条件）。
- 示例：
  - `SELECT * FROM films`：查询 `films` 表所有字段、所有行；
  - `SELECT * FROM films WHERE language = '日语'`：只查语言为日语的影片；
  - `SELECT * FROM films WHERE id = 1`：查 ID 为 1 的记录。
- 在 Python 中执行查询需配合 `fetch`：
  - `cur.execute(...)` 后必须跟 `cur.fetchall()`（或 `fetchone()`/`fetchmany()`）才能获取结果；
  - 原因：`execute` 仅发送指令，`fetch` 才真正取回数据。

## DELETE、UPDATE、DROP 等 DML/DLL 语句 [原片 @ 21:12](https://www.bilibili.com/video/BV1AR8U6REzY?t=1272)

- `DELETE FROM films WHERE id = 1`：删除符合条件的记录（需 `commit`）。
  - **严重警告**：若遗漏 `WHERE` 子句（如 `DELETE FROM films`），将**清空整张表**。
- `UPDATE films SET title = '新片名' WHERE id = 1`：更新指定记录的字段值。
- `DROP TABLE films`：**删除整张表及其结构**（即“删库跑路”），比 `DELETE` 更彻底。
- 所有修改数据的操作（INSERT/UPDATE/DELETE/DROP）均需 `commit`；纯查询（SELECT）无需。

## SQL 注入原理与参数化查询防护 [原片 @ 24:49](https://www.bilibili.com/video/BV1AR8U6REzY?t=1489)

- **SQL 注入**定义：将恶意命令伪装成用户输入数据，利用字符串拼接漏洞篡改 SQL 逻辑。
- 演示案例：
  - 正常查询：`WHERE title = '肖申克的救赎'`
  - 恶意输入电影名：`' OR 1=1 -- `（开头单引号提前闭合原引号）
  - 拼接后 SQL 变为：`WHERE title = '' OR 1=1 -- '` → `1=1` 恒真，`--` 注释掉后续内容 → **全表泄露**。
- **防护方案：参数化查询（Parameterized Query）**：
  - 危险写法（拼接）：`"WHERE title = '" + user_input + "'"` ❌
  - 安全写法（占位符）：
    ```python
    cur.execute("SELECT * FROM films WHERE title = ?", (user_input,))
    ```
  - Python 驱动会自动转义参数值，确保其仅作为**数据**而非**代码**执行。
- 此方法适用于所有需传参的 SQL 语句（SELECT/INSERT/UPDATE/DELETE）。

## ORDER BY、DESC、LIMIT 实战 [原片 @ 30:43](https://www.bilibili.com/video/BV1AR8U6REzY?t=1843)

- `ORDER BY created_at`：按 `created_at` 字段升序（默认）排列；
- `ORDER BY created_at DESC`：按 `created_at` 字段降序排列（最新在前）；
- `LIMIT 5`：只返回前 5 条结果。
- 组合使用示例：`SELECT * FROM films ORDER BY created_at DESC LIMIT 5` → 获取**最近入库的 5 条电影**。
- 对比文件存储方案：
  - 文件版：需全量读入内存 → Python 排序 → 切片取前 N；
  - 数据库版：一行 SQL 声明意图（“我要最近 5 条”），数据库内部优化执行；
  - 本质区别：文件版是 **“怎么做”（how）**，SQL 是 **“要什么”（what）**。

## 数据库排序机制：内存堆筛法与外部归并排序 [原片 @ 36:01](https://www.bilibili.com/video/BV1AR8U6REzY?t=2161)

- 场景：大数据量下执行 `ORDER BY ... LIMIT 10`。
- **小数据量（内存充足）**：使用**最小堆/最大堆筛法**：
  - 开辟 10 个内存位置；
  - 先载入 10 条，建堆（如最大堆）；
  - 逐条读取剩余数据，与堆顶比较：若更大，则替换堆顶并调整堆；
  - 最终堆内即为全局 Top 10。
- **大数据量（内存不足）**：采用**外部归并排序（External Merge Sort）**：
  - 分批读入（如每次 8 条），内存内排序后写为有序临时文件（“有序段”）；
  - 所有数据处理完后，硬盘上存在多个有序段；
  - 合并阶段：从每个有序段取最大值入内存比较，选出全局最大者输出；该段次大值补位，继续比较 → 循环实现全局有序输出。
- 此机制避免内存溢出，但代价是**大量磁盘 I/O，速度变慢**。

## 索引的本质、价值与三大代价 [原片 @ 41:04](https://www.bilibili.com/video/BV1AR8U6REzY?t=2464)

- **索引（Index）**：为特定字段（如 `created_at`）预先构建的、按该字段值排序的**独立数据结构**（类似书的目录）。
- **价值**：极大加速基于该字段的查询、排序、范围查找。
  - 示例：`ORDER BY created_at DESC LIMIT 10` → 直接定位索引末尾 10 条 → 按索引指针找到对应主表记录 → **一次定位，无需全表扫描或排序**。
- **三大代价**：
  1. **空间代价**：索引本身占用额外磁盘空间；
  2. **写入代价**：每次 INSERT/UPDATE/DELETE 时，数据库需同步维护索引，写入变慢；
  3. **人工管理代价**：除主键等少数情况外，**索引需开发者显式创建**（如 `CREATE INDEX idx_created_at ON films(created_at)`），不能“雨露均沾”，应只对**高频查询/排序/筛选字段**建立。
