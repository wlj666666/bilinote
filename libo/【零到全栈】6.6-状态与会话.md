## 会话问题的提出：历史记录混用现象 [原片 @ 00:00](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=0)

- 视频以“文字实验室”前端页面为例，用户查询历史已存入数据库，并可通过 `/api/history` 接口读取。
- 当前问题：刷新页面后历史记录消失；更严重的是，在不同浏览器（如 Chrome 与 Safari）中访问同一 `localhost:3000` 地址时，**所有用户看到的是完全相同的历史记录列表**。
- 根本原因：服务端未区分用户身份，所有记录均存于同一张数据库表中，查询时不加任何用户标识过滤。
- 后果：若上线发布，任意访客均可查看他人全部分析记录，隐私完全失控。
- 目标：让网站“认人”，使每个用户仅能访问自身专属的历史数据。

## HTTP 无状态的本质与意义 [原片 @ 03:44](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=224)

- HTTP 协议是 **stateless（无状态）** 的：每次请求处理完毕，服务端即“遗忘”该请求及其上下文；下一次请求对服务端而言是全新的、与前次无关的独立事件。
- 这并非缺陷，而是针对海量、短暂、彼此无关请求场景的**刻意设计选择**，保障了可扩展性。
- 对比：SSH 是有状态连接，服务器维持用户当前目录等现场；HTTP 则不维持任何现场。
- 无状态的优势：
  - 任意服务器节点均可处理任一请求，便于水平扩展与负载均衡；
  - 单台服务器宕机不影响其他用户会话（因无状态数据不依赖特定机器）；
  - 内存占用可控（无需为每个用户长期保存状态）。
- 代价：应用层需自行解决“认人”问题，即在无状态协议之上构建有状态的业务逻辑。

## 状态（state）的计算机定义 [原片 @ 09:02](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=542)

- “状态”（state）在计算机术语中，指**一组决定系统下一步行为的参数集合**，而非日常语境中的“精神状态”。
- 示例：游戏暂停时的关卡、血量、装备、机关开关状态，共同构成该局游戏的 state。
- 状态的两个核心特征：
  1. **决定后续行为**（如剩余血量决定能否扛住下一击）；
  2. **默认易失**（如关机后丢失），需通过“存档”（如写入硬盘）持久化。
- 在 `zero-to-tech` 项目中，状态已存在于多个层级：
  - 浏览器内存（刷新即丢）；
  - Python REPL 内存（退出即丢）；
  - SQLite 数据库（关机重启仍存）。
- 当前挑战不是“状态存多久”，而是“**如何让同一用户的多次 HTTP 请求共享状态**”。

## 有状态 vs 无状态：适用场景与权衡 [原片 @ 11:53](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=713)

- SSH 适合有状态：面向少量、长时间、连续交互的连接，维持现场（如当前路径）是必要且高效的。
- HTTP 适合无状态：面向海量、极短、彼此无关的请求，强制维持现场将导致：
  - **内存爆炸**：100 万并发用户需存 100 万份现场；
  - **负载均衡困难**：请求必须路由至同一台服务器（因现场仅存于该机）；
  - **单点故障风险**：某台服务器宕机，其上所有用户现场丢失。
- 结论：无状态是 HTTP 面向互联网规模扩张的关键基石；而人类活动天然需要“记忆”（状态），因此必须在应用层以最小代价重建会话。

## 会话（session）与 Cookie 的机制辨析 [原片 @ 18:08](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=1088)

- **会话（session）**：是一种**逻辑认定**，指将一系列原本独立的 HTTP 请求，认定为同一用户的一次连续交互。它本身不是数据，而是一段关系。
- **Cookie**：是一套**传输机制**，由浏览器实现：服务端通过 `Set-Cookie` 响应头发送一小段数据（如 `session_id=abc123`），浏览器自动存储并在后续同源请求的 `Cookie` 请求头中回传。
- 关键区别：
  - Session 是概念（“谁是谁”），Cookie 是工具（“怎么传 ID”）；
  - Cookie 可用于传递任意信息（如主题偏好、语言设置），不限于 `session_id`；
  - 会话也可不依赖 Cookie（如移动端 App 使用自定义 `token` 请求头传递 `session_id`）。
- 二者关联：服务端为会话生成唯一 `session_id`，通过 `Set-Cookie` 发送给浏览器；浏览器后续请求携带该 `session_id`，服务端据此识别用户，从而将无状态请求串成有状态会话。

## 实现会话的三要素：ID、存储、传递 [原片 @ 22:23](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=1343)

为使文字实验室支持用户级历史记录，需完成三件事：
1. **服务端生成并管理会话 ID（`session_id`）**：需满足唯一性、不可预测性（防伪造）；
2. **数据库增加字段**：在 `history` 表中新增 `session_id TEXT` 字段，用于关联每条记录所属会话；
3. **建立 ID 传递通道**：利用 Cookie 机制，在浏览器与服务端间可靠传递 `session_id`。

## 技术选型：UUID 作为 session_id [原片 @ 23:03](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=1383)

- 选用 Python 标准库 `uuid.uuid4()` 生成 `session_id`：
  - `uuid4()` 生成基于随机数的 UUID，重复概率极低（类比宇宙沙粒相撞）；
  - 满足唯一性与不可预测性要求；
  - 一行代码即可生成，简单可靠。
- 示例：`uuid.uuid4()` 输出形如 `f81d4fae-7dec-11d0-a765-00a0c91e6bf6` 的字符串。

## Cookie 的结构与安全属性 [原片 @ 24:50](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=1490)

- 完整的 `Set-Cookie` 响应头示例：
  ```
  session_id=f81d4fae-7dec-11d0-a765-00a0c91e6bf6; Max-Age=2592000; HttpOnly; SameSite=Lax; Path=/
  ```
- 组成部分：
  - **内容部分**（`session_id=...`）：键值对，浏览器回传给服务端的核心标识；
  - **属性部分**（`; Max-Age=...; HttpOnly; ...`）：写给浏览器的指令，浏览器执行后不回传：
    - `Max-Age`：有效期（秒），不设则为会话级 Cookie（关闭浏览器即失效）；
    - `HttpOnly`：禁止 JavaScript 访问，防御 XSS 攻击；
    - `SameSite`：限制跨站请求携带 Cookie，增强安全性；
    - `Path`：指定 Cookie 作用路径，默认 `/` 表示全站有效。

## 跨源（CORS）下 Cookie 传递的配置要求 [原片 @ 26:21](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=1581)

- 前后端分离开发（如前端 `localhost:5173`，后端 `localhost:8000`）构成跨源（CORS）。
- 浏览器安全策略默认**跨源请求不携带 Cookie**。
- 解决方案需**前后端协同配置**：
  - **后端（FastAPI）**：在 CORS 中间件启用 `allow_credentials=True`；
  - **前端（fetch/axios）**：发起请求时显式声明 `credentials: 'include'`（或 `withCredentials: true`）。
- 缺一不可，否则 Cookie 无法在跨源场景下传递。

## 项目改造全流程：前后端与数据库协同 [原片 @ 27:11](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=1631)

1. **CORS 配置**：
   - 后端：`app.add_middleware(CORSMiddleware, ..., allow_credentials=True)`
   - 前端：`fetch(..., { credentials: 'include' })`（两处关键请求：`/api/analyze` 和 `/api/history`）

2. **数据库改造（`storage.py`）**：
   - 修改 `init_db()`：建表 SQL 新增 `session_id TEXT` 字段；索引改为 `(session_id, created_at)` 复合索引（提升按会话查历史的效率）；
   - 删除现有 `history.db` 文件，重启后端触发新表结构重建。

3. **服务端逻辑（`main.py`）**：
   - 引入 `uuid`, `Request`, `Response`；
   - 定义 `get_session_id(request: Request, response: Response)` 函数：从请求 `Cookie` 读取 `session_id`，若无则生成新 UUID 并通过 `response.set_cookie()` 设置；
   - 在 `/api/analyze` 和 `/api/history` 接口中调用 `get_session_id` 获取当前会话 ID。

4. **数据存取逻辑（`storage.py`）**：
   - `save_record()`：新增 `session_id` 参数，INSERT 语句包含该字段；
   - `get_history()`：新增 `session_id` 参数，SELECT 语句添加 `WHERE session_id = ?` 条件。

## 验证：浏览器 DevTools 中观察 Cookie 行为 [原片 @ 39:50](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=2390)

- 在浏览器开发者工具中可直观验证：
  - **Application → Storage → Cookies**：查看已存储的 `session_id` 值；
  - **Network → 任一请求 → Request Headers → Cookie**：确认请求头中是否自动携带 `session_id=...`；
  - **Network → 任一响应 → Response Headers → Set-Cookie**：确认服务端是否返回 `Set-Cookie` 头。
- 注意：`curl` 默认不存 Cookie，故重复调用会得到不同 `session_id`；浏览器则自动管理并回传。

## 会话的局限性：非身份认证 [原片 @ 43:23](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=2603)

- 当前基于 Cookie 的会话（session）**不等于用户身份认证（Authentication）**：
  - Cookie 可被清除、过期（`Max-Age` 到期）、跨设备/浏览器失效；
  - 无法区分“同一人”与“同一浏览器实例”，不具备长期、强身份绑定能力。
- 真正的身份认证需在此基础上叠加：
  - 用户注册与登录流程；
  - 密码安全（哈希、盐值）；
  - 密码找回、验证码等机制。
- 但所有这些高级认证体系，都**必须以会话机制为基础**。

## 大模型“会话”的本质：上下文（context）传递 [原片 @ 44:11](https://www.bilibili.com/video/BV1Q6bH6xEZS?t=2651)

- 大模型 API（如 DeepSeek）本身是无状态的：每次调用独立，模型不保留任何历史。
- 所谓“记住上文”，实则是**客户端（前端/AI Agent）在每次请求时，将完整对话历史（`messages` 数组）作为上下文（context）一并发送给模型**。
- `messages` 结构示例：
  ```python
  messages = [
      {"role": "system", "content": "..."},  # 系统提示词
      {"role": "user", "content": "我的名字叫李勃"},  # 用户第一轮输入
      {"role": "assistant", "content": "好的李勃，我记住了"},  # 模型第一轮回复
      {"role": "user", "content": "我叫什么名字？"}  # 用户第二轮输入（含全部历史）
  ]
  ```
- 关键点：
  - “记忆”存储在客户端，而非模型侧；
  - 每次请求需携带全部相关历史，成本随轮次增长（Token 计费、上下文窗口限制）；
  - AI Agent 工具（如 DeepSeek Harness、Codex、WorkBuddy）的核心工作，就是智能管理这个上下文（知识库、Skill 等概念均服务于上下文裁剪与注入）。

## AI 总结

本节核心是理解“状态”与“会话”在 Web 开发中的本质与实践。HTTP 协议天生无状态，这是其支撑互联网规模的基石，但也意味着服务端默认“不认人”。视频通过文字实验室的历史记录混用问题，引出 `session`（会话）这一应用层解决方案：服务端生成唯一、不可预测的 `session_id`（常用 UUID），通过 `Set-Cookie` / `Cookie` 机制在浏览器与服务端间传递，并在数据库中以 `session_id` 字段关联用户专属数据。这本质上是在无状态协议之上，以最小代价（仅传递 32 字符 ID）重建用户连续性。值得注意的是，这种 Cookie 会话不等于身份认证，它脆弱且易失效；而大模型的“会话”则是另一条路径——将状态（上下文）完全交由客户端维护并每次全量传递。二者虽机制迥异，但目标一致：在底层无状态约束下，为人类连续、有意义的交互提供支撑。
