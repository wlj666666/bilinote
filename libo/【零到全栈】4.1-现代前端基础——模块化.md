## 传统 script 引入方式分析 [原片 @ 06:28](https://www.bilibili.com/video/BV1fmEi6DE9b?t=388)

以 `index.html` 为例，当前引入方式为：

- 多个 `<link rel="stylesheet">` 引入本地 CSS 文件（共 8 行）；
- 多个 `<script src="...">` 引入本地 JS 文件（`cards.js`, `score.js`, `nav.js`）；
- 额外一行 `<script src="https://cdn.jsdelivr.net/npm/animejs@3.2.1/lib/anime.min.js">` —— 此为 **CDN 引用**。

关键观察：
- 所有资源均通过 `<script>` 或 `<link>` 标签声明；
- 浏览器不区分本地路径或远程 URL，只要可访问即加载；
- CDN 引用仅是“省去本地存储”的便捷方式，功能等价于下载 `anime.min.js` 后本地引用。

## CDN 引用与第三方库概念 [原片 @ 07:39](https://www.bilibili.com/video/BV1fmEi6DE9b?t=459)

- **CDN 引用**：指通过 HTTPS URL 直接加载托管在公共服务器上的 JS 文件。
- **第三方库**：非官方、非自研的现成脚本库（如 `anime.js`），用于快速实现特定功能（动画、图表、日期处理等）。
- `anime.js` 的使用机制：
  - 加载后，在全局 `window` 对象上挂载 `anime` 变量；
  - 其他 JS 文件（如 `cards.js`）通过 `anime.animate(...)` 直接调用；
  - 此种共享方式依赖全局命名空间（`window.anime`）。

> 第三方库极大提升开发效率，但其全局挂载方式埋下隐患。

## 全局污染与加载顺序问题 [原片 @ 15:43](https://www.bilibili.com/video/BV1fmEi6DE9b?t=943)

### 问题一：脚本加载顺序强依赖  
- `cards.js` 必须在 `anime.js` **之后**加载，否则报错 `anime is not defined`；  
- 该依赖关系**未在代码中声明**，仅靠 HTML 中 `<script>` 标签顺序隐式维护；  
- 一旦顺序错误（如将 `anime.js` 移至 `cards.js` 下方），动画失效且控制台报错；  
- 项目规模扩大（数十上百 JS 文件）时，人工维护顺序极易出错。

### 问题二：全局变量名冲突（全局污染）  
- 多个第三方库均向 `window` 写入变量（如 `chart`, `date`, `utils`）；  
- JavaScript 全局作用域中同名变量会被后加载者覆盖；  
- 命名冲突无法完全避免（开发者无法穷举全球所有变量名）；  
- 导致难以排查的隐蔽 bug，AI 亦难以辅助定位。

> 这两类问题源于早期（1995 年设计）的 script 机制，已无法满足现代 Web 工程复杂度需求。

## ES Modules 模块化机制介绍 [原片 @ 22:07](https://www.bilibili.com/video/BV1fmEi6DE9b?t=1327)

- **模块化核心思想**：打破全局共享，默认封闭，显式导出/导入。
  - 每个 JS 文件默认作用域隔离（仅自身可见）；
  - 若需对外提供功能，必须使用 `export` 显式声明；
  - 若需使用他人功能，必须使用 `import` 显式声明依赖。

- **语法来源**：ES6（ECMAScript 2015）正式引入 `import` / `export`；
- **术语说明**：
  - `ES` = ECMAScript（语言规范）；
  - `JS` = JavaScript（按规范实现的语言）；
  - `ES6` = ECMAScript 第六版（即 2015 版规范）；
  - `ES Modules`（简称 ESM）= 基于该规范的模块系统。

> 不需记忆语法细节，重点理解其解决的问题：**依赖关系显式化 + 作用域隔离**。

## 模块化改造五步实操 [原片 @ 25:02](https://www.bilibili.com/video/BV1fmEi6DE9b?t=1502)

基于 `zero-to-tech-demos` 仓库 README 提供的步骤：

1. **改造 `cards.js`**  
   - 替换原内容为含 `import { animate, stagger } from 'https://cdn.jsdelivr.net/npm/animejs@3.2.1/lib/anime.min.js';` 和 `export function initCards() { ... }` 的模块化写法。

2. **改造 `score.js`**  
   - 同样添加 `import` 语句引入 `anime`，并用 `export` 导出初始化函数。

3. **改造 `nav.js`**  
   - 同样添加 `import` 与 `export`，导出导航高亮逻辑。

4. **新建 `js/main.js`（总入口）**  
   - 内容为统一 `import` 上述三个模块，并调用其导出函数：  
     ```js
     import { initCards } from './cards.js';
     import { initScore } from './score.js';
     import { initNav } from './nav.js';
     initCards();
     initScore();
     initNav();
     ```

5. **修改 HTML 中的 script 引入方式**  
   - 删除原有 4 行 `<script src="...">`；  
   - 替换为单行：  
     ```html
     <script type="module" src="./js/main.js"></script>
     ```
   - 同样修改 `text-lab.html` 中对应部分。

> 改造后，所有依赖关系均在 JS 代码内明确定义，HTML 不再承担顺序管理职责。

## 模块化对浏览器运行环境的新要求 [原片 @ 31:41](https://www.bilibili.com/video/BV1fmEi6DE9b?t=1901)

- **强制要求 HTTP(S) 服务**：  
  - 启用 `type="module"` 后，浏览器**禁止**通过 `file://` 协议直接打开 HTML 文件；  
  - 必须通过 Web Server（如本地开发服务器、Nginx、或已部署的公网服务器）提供服务；  
  - 否则控制台将报 CORS 相关错误，模块无法加载。

- **原因**：安全机制限制（涉及跨域策略与模块解析沙箱），具体细节未展开。

> 实际操作中，需将改造后的代码推送至服务器并访问其 HTTP 地址（如 `http://182.254.229.21/index.html`）才能正常运行。

## ES Modules 的历史背景与演进 [原片 @ 34:13](https://www.bilibili.com/video/BV1fmEi6DE9b?t=2053)

- JavaScript 诞生于 1995 年，但**2015 年（ES6）之前无官方模块系统**；
- 早期工程师自发探索方案（如 CommonJS、AMD），但均为非标准、环境受限；
- ES6 正式确立 `import`/`export` 语法，成为**标准化模块机制**；
- 浏览器原生支持时间较晚：
  - 2017 年前后，Chrome、Safari、Firefox、Edge 等主流浏览器陆续支持 `type="module"`；
- 截至视频录制时（2026 年），ES Modules 在浏览器端可用尚不足十年。

> “现代前端”之“现代”，正在于此——它是一套非常年轻、仍在快速演进的工程实践体系。

## AI 总结

本节课以真实小网站为载体，系统揭示了从传统前端迈向现代前端的关键跃迁：通过 ES Modules 实现代码模块化。核心价值在于将隐式的全局依赖（靠 HTML 标签顺序和 window 命名空间维系）转化为显式的、代码内声明的 import/export 关系，从而根治加载顺序混乱与全局污染两大顽疾。这一转变虽仅涉及几行语法改动，却标志着前端工程从“脚本拼凑”走向“可维护、可扩展、可协作”的系统化开发范式——而这一切，正建立在不到十年即被主流浏览器广泛支持的 ES6 模块标准之上。
