# 多用户并发与 GPU 资源配置：压测记录及参数选择依据

测试日期：2026-10-16。本文记录同一次压测的结果及后续确认的参数；整理文档时未重新运行 GPU 压测。

已采用配置：全站工作流并发 **6**，GPU 计算名额 **1**，CPU 阶段 **2**，总结接口 **2**。这里的工作流包括下载、等待资源、推理、总结和保存；6 个工作流不代表 6 个模型同时占用 GPU。每用户执行 1、每用户排队 3、全站排队 20。

本次已验证工作流并发 12 可以完成测试任务，但短素材在 6 之后吞吐没有明显收益。因此 6 是当前素材组合的建议运行值，12 是本次验证到的并发数，不能据此断言硬件绝对上限是 12。压测完成后，按用户确认已将代码、启动脚本和配置中的工作流默认值由 3 调整为 6；GPU/CPU/API 名额仍为 1/2/2，可选模型共驻留保持关闭。已运行的后端需重启后读取新值。

## 各参数为什么这样选

| 参数 | 原值 → 已采用值 | 选择理由与证据范围 |
| --- | --- | --- |
| `TASK_MAX_WORKERS` | 3 → **6** | 默认卸载策略下，12 个短素材任务耗时由 59.21 秒降至 51.71 秒；提高到 9 为 52.34 秒。缓存策略的 6/9/12 对比与长素材 6/12 对比，也未显示超过 6 后总体吞吐提升。选择当前负载的收益拐点，兼顾进程开销。 |
| `TASK_GPU_SLOTS` | 1 → **1** | 独立 Whisper 实验中，同样 12 次推理的 GPU 并发 1/2/3/4 耗时为 38.84/78.66/89.26/92.36 秒；增加并发时显存增加、总吞吐下降。混合工作流中 Whisper 和 CUDA OCR 共用这一个名额。详见下文适用边界。 |
| `TASK_CPU_SLOTS` | 2 → **2** | 全流程在 2 个 CPU 密集阶段额度下完成，未观察到需要扩大 CPU 名额的证据。它限制阶段数，不等于使用两个 CPU 核；本轮没有逐级比较 CPU 名额 1/2/4，不能宣称 2 是 CPU 性能最优值。 |
| `TASK_API_SLOTS` | 2 → **2** | 控制同时在途的总结请求。压测用固定 6 秒的模拟接口，未测真实供应商 RPM/TPM，因此保持原值，不按 GPU 余量提高。2 个并发也不自动保证供应商配额足够。 |
| `TASK_USER_ACTIVE` | 1 → **1** | 公平性规则，避免一个用户占满执行名额；用户之间轮流领取任务。本轮检查每用户活跃数不超过 1，不把这个数当作硬件极限。 |
| `TASK_USER_QUEUE_LIMIT` | 3 → **3** | 限制单用户连续提交，避免占满队列；本轮突发测试检查单用户排队不超过 3。这是服务策略，没有比较更大队列对业务体验的影响。 |
| `TASK_QUEUE_LIMIT` | 20 → **20** | 为积压设置明确上限。每组 80 次突发提交、32 路并发，在暂停领取时接收 20、返回 429 拒绝 60。20 是已验证的接单策略，不是数据库最多只能保存 20 条任务。 |
| `WHISPER_KEEP_DURING_OCR` | 0 → **0，关闭** | 共驻留测试有小幅收益，但更依赖显存余量和模型/素材，当前先使用卸载策略。设为 1 属于后续可选优化，不是已默认开启。 |
| `OCR_GPU_RESERVE_MIB` | 3072 → **3072 MiB** | 仅在开启上述共驻留时使用。OCR 启动前空闲显存不足或无法测量就卸载 Whisper。它是预留门槛，未逐档调优，不是 OCR 对任意输入的显存需求保证。 |
| `WHISPER_CPU_THREADS` | 2 → **2** | 限制转写内部 CPU 线程；避免多进程同时扩大内部线程数。保持本轮已测值，未单独比较线程数的最优点。 |
| `VIDEO_FRAME_WORKERS` | 2 → **2** | 控制单任务抽帧内部并发，FFmpeg 单进程线程限制为 1；避免工作流并发翻倍时抽帧线程无约束扩张。 |
| `EMBEDDING_CPU_THREADS` | 2 → **2** | 索引/问答 embedding 固定 CPU provider，ONNX 内部线程限制为 2，跨操作线程为 1。避免索引在 GPU 名额之外偷偷占显存。 |
| `OCR_THREADS` | 1 → **1** | 控制 OCR 内部 ONNX 线程，保持本轮已测值；不等于 GPU 只运行一个计算线程，也不表示 OCR 能同时处理多个任务。 |

前三类数字的含义不同：工作流名额决定有多少任务已被领取，阶段名额决定哪些任务此刻能用某项资源，内部线程数控制单个操作的 CPU 并行。参数值不代表给每个客户固定划分 CPU/GPU 百分比。超时、心跳和重试参数沿用 [任务调度说明](TASK_SCHEDULING.md) 中的值，本轮没有对它们做性能调优。

## 机器和测量范围

- GPU：NVIDIA GeForce RTX 5060 Laptop GPU，8151 MiB 显存。
- 当前 Linux/WSL 环境：32 个逻辑 CPU，可见内存约 15.5 GiB；开始时可用约 12.5 GiB。CPU 百分比为整个可见主机的占用，非单核百分比。
- ASR：已有本地 faster-whisper large-v3，CUDA / int8_float32。OCR：项目已有 CUDA RapidOCR 路径。使用相同识别配置比较并发，不切换小模型。
- 使用独立临时数据库、模拟用户、真实认证令牌、私有上传文件、独立调度器及推理进程，正式用户数据库仅读取是否有执行/排队任务。测试数据结束后删除，报告与日志另行保留。
- 真实执行：生成接口、认证、队列、进程调度、媒体解码、ASR、OCR、状态轮询、笔记保存和 CPU 向量索引。已有字幕的任务使用模拟字幕响应。总结接口模拟固定 6 秒等待，不请求外部模型、不产生付费 API 费用。
- 请求通过 FastAPI TestClient/ASGI 发出，未覆盖公网隧道、浏览器渲染、外网下载带宽、真实总结供应商的响应速度及 RPM/TPM 限制。下表吞吐只适用于给定素材与模拟总结时长，不能直接当作任意客户视频每分钟处理量。
- 每组在新进程中执行；每组工作流结束后，另用 32 个并发请求发起 80 次提交验证拒绝规则。该突发测试暂停调度领取，便于单独验证 20 个排队名额。
- 约每 0.4 秒采样显存、GPU 使用率、温度、主机内存和 CPU。显存使用超过 91%、可用内存连续三次低于 2500 MiB、GPU 达到 86℃、或真实客户任务到达时停止实验。采样峰值可能遗漏极短瞬时峰值。

## GPU 同时计算：1 个更快

同一 Whisper 模型共享多个 worker，每组处理 12 次相同的 30 秒真实语音；模型预热后计时，不含首次加载。每组任务总数和输入相同，变化的是同时计算的任务数。并发 1 表示依次算完全部 12 次，而非只运行一次。实验通过调整共享模型的 `num_workers` 对比，并非为每个任务单独加载一整套 Whisper 模型。单独突破实验进程中的 GPU 并发，正式调度器仍限制 GPU 名额为 1。

| 同时推理 | 全部完成耗时 | 次/分钟 | 单次推理 P95 | 采样显存峰值 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 38.84 秒 | 18.54 | 3.26 秒 | 2781 MiB |
| 2 | 78.66 秒 | 9.15 | 14.02 秒 | 3941 MiB |
| 3 | 89.26 秒 | 8.07 | 23.45 秒 | 5037 MiB |
| 4 | 92.36 秒 | 7.80 | 31.99 秒 | 6165 MiB |

4 组均 12/12 成功，转写文本哈希一致。随后重复并发 1：38.72 秒、18.59 次/分钟，结果接近首轮。当前机器、模型和输入下，增加 CUDA 并行既增加显存，也降低总吞吐，因此不建议提高 `TASK_GPU_SLOTS`。该实验没有探测 GPU 显存耗尽点。

原始数据：[GPU 汇总](data/concurrency_benchmark/gpu-summary.json)、[并发 1 复测](data/concurrency_benchmark/gpu-1-repeat.json)。

### 为什么显存用得更多，速度却更慢

显存用于保存模型权重、输入和计算过程中的临时数据；计算单元、显存带宽、CPU 数据准备和运行时调度共同影响处理速度。空闲显存表示还放得下更多数据，不等于有相同比例的算力闲置。一个用户任务本身也能启动大量 GPU 计算，并非只占用 GPU 的一个计算单元。

本次共享模型增加 worker 后，额外的执行状态和工作区使显存峰值从 2781 MiB 增至 6165 MiB，但每分钟完成数从 18.54 降至 7.80。因此，以“同样工作量更快完成”为目标时，应选择这轮测得的 GPU 并发 1。以显存占满作为调参目标会得出相反选择，无法改善本次吞吐。

这里要区分实测事实与原因解释：已测事实是当前实现增加 GPU 并发后更慢；计算/带宽争用、同步及调度开销是可能原因。本轮没有做算子级性能分析，不能断言某一种原因已经被证实，也不能断言单任务已达到 100% 理论算力。`nvidia-smi` 采样中的 GPU 使用率也不能等同于理论算力使用比例。

GPU 独立对比只覆盖同一份 30 秒语音的 Whisper 推理，未比较多个 OCR 同时计算、ASR 与 OCR 同时计算或不同批处理方案。混合任务测试则是在 GPU 名额为 1 的前提下比较工作流数量。故当前值结合了已测 Whisper 结果、已验证的混合调度路径及单卡推理架构，不能外推为所有 GPU 应用都应串行。并发 2/3/4 的耗时差异较大，足以支持本轮选择；每个档位仅跑一组、并发 1 另复测一次，未计算统计置信区间。

当前 `TaskLimits.from_env()` 还要求 `TASK_GPU_SLOTS=1`；独立 GPU 实验不经过这个正式调度限制。以后若要研究其他 GPU 并行策略，需要同时调整推理服务的生命周期和资源管理，并重新验证吞吐、显存及识别结果，不能仅修改环境变量。

### 三个任务都需要 GPU 时如何执行

工作流名额为 6 时，A、B、C 都可以被领取。假设当前 A 获得 GPU，B、C 则等待资源；GPU 阶段结束时释放名额，不会一直占到整篇笔记生成结束。

| 时段 | 任务 A | 任务 B | 任务 C |
| --- | --- | --- | --- |
| A 的 GPU 阶段 | GPU 转写/识别 | 等待 GPU | 等待 GPU |
| B 的 GPU 阶段 | 请求总结或保存结果 | GPU 转写/识别 | 等待 GPU |
| C 的 GPU 阶段 | 已完成或继续后续步骤 | 请求总结或保存结果 | GPU 转写/识别 |

上表为说明阶段重叠的示例，不保证 A/B/C 的 GPU 获取顺序；实际由资源名额释放后的竞争决定。按用户轮流调度发生在领取工作流时，并非对 GPU 阶段进行固定轮转。GPU 阶段通常还需同时取得一个 CPU 阶段名额，等待时不会一直占着部分资源。

如果三个任务当前都只有 GPU 计算需要执行，GPU 计算阶段会依次进行；工作流并发增加不会让这三个计算阶段同时加速。工作流 6 的收益来自让其他阶段与 GPU 工作重叠。

### 富余显存可以用来减少模型加载

让权重留在显存与同时执行多个推理是两件独立的事。开启 `WHISPER_KEEP_DURING_OCR=1` 后，显存充足时允许 Whisper 保留权重，OCR 使用独立进程计算；两者仍共用一个 GPU 计算名额。

同样的 12 个短素材任务、工作流并发 6，默认卸载策略为 51.71 秒、显存峰值 2781 MiB；保留策略为 49.04 秒、峰值 3124 MiB，整组耗时减少约 5.2%。这是本次富余显存的一种有效用途，但不是翻倍提速。长素材的缓存策略在工作流 6 下峰值为 3677 MiB。

当前采用值仍为关闭，保留策略作为有实测支持的可选项。3072 MiB 门槛只检查 OCR 启动前空闲显存；模型变化、图像尺寸、OCR 工作区及其他进程占用都会改变余量。开启时需保留监控和重新测量，不能把本轮的峰值视为任意输入的上限。

## 本轮测试合计

修复后完成 10 组全流程测试，共 132/132 个任务完成并建立索引；每组附带一次突发测试，合计 800 次提交，200 次接收、600 次 HTTP 429，无其他状态。突发响应 P95 为 0.435～0.544 秒；任务执行期间的状态轮询 P95 为约 0.004～0.005 秒。另有 60 次独立真实 Whisper 推理完成：并发 1/2/3/4 四组加并发 1 复测，共 5 组，每组 12 次。早先文档写为 72 次，现按已保存的原始记录校正为 60 次。

这些是本轮有限批次的结果，未覆盖数小时持续运行、任意长视频、不同模型、不同用户素材以及真实外部服务异常。推荐配置对应本机与此次混合负载，后续更换输入或接口延迟后可用同一脚本复测。

## 并发提交发现的问题和修复

首轮所有 12 个任务完成，但后续突发提交暴露了数据库连接池等待：认证依赖一直持有一个连接，业务代码再申请另一个；大量请求同时占满池后等待 30 秒超时。历史列表在持有外层连接时逐项查状态，也有相同风险。

现已把认证查询和历史查询的连接及时关闭，再进入后续业务查询；没有以无限扩连接池掩盖问题。新增只有 1 个连接的池、8 路并行读取队列/历史共 32 次的回归测试。修复后的各组突发提交符合队列限制：接收 20、HTTP 429 拒绝 60，无其他状态。正式队列满时应向用户提示稍后重试，不能无限接单。

另发现 Chroma 默认 embedding 可能选用可用 GPU provider，从而绕过资源名额。现显式固定为 CPU、ONNX 内部线程 2，索引和查询均受 CPU 阶段额度限制；保持原有 MiniLM 权重和维度，回归验证旧默认索引仍可打开。

修复后运行 `python -m pytest tests/test_task_scheduling.py -q`：24 项全部通过；相关 Python 编译检查与 `git diff --check` 通过。

初次失败记录保留在 [原始日志](data/concurrency_benchmark/pipeline-1-before-auth-fix.log) 和 [失败汇总](data/concurrency_benchmark/pipeline-summary-before-auth-fix.json)。

## 推荐使用方式与复现

当前代码、启动脚本及配置已使用工作流并发 6。下列命令显式写出主要额度，便于核对或复现部署；已运行的旧进程需先正常停止再启动：

```bash
cd /home/unbekannter/bilinote/BiliNote/backend
TASK_MAX_WORKERS=6 TASK_GPU_SLOTS=1 TASK_CPU_SLOTS=2 TASK_API_SLOTS=2 bash start-gpu.sh
```

当前机器和已测模型也可以加入 `WHISPER_KEEP_DURING_OCR=1 OCR_GPU_RESERVE_MIB=3072` 使用可选缓存策略。确认总结供应商的请求/Token 配额后再调整 `TASK_API_SLOTS`；本次模拟总结没有验证这一部分。工作流 6 与 GPU 1 是分别管理的额度，无需按用户分配固定 GPU 百分比。
